# dex_teleop

`dex_teleop` converts independently acquired hand articulation and wrist pose
into robot-hand joint commands and connects those commands to OmniGibson
teleoperation. Tracking, synchronization, retargeting, and simulator execution
are independent boundaries:

```text
articulation source ---+
                       +--> synchronized hand observation --> retargeter --> OmniGibson adapter
wrist-pose source -----+
```

The canonical observation retains named, wrist-local joints (using the OpenXR
joint vocabulary where possible), per-joint validity, source timestamps, and
the independently selected reference-frame wrist pose. A compatibility
conversion still produces the 21-landmark `HandFrame` consumed by the existing
adaptive retargeter. DexPilot opts into the rich observation contract, then
selects its MediaPipe-equivalent position objective without a world-frame
round trip. Orientations remain available to future retargeters. Pink/V2D is
not an implemented backend.

`HandArticulationSample.coordinate_frame` and
`WristPoseSample.anatomical_frame` make the local-basis contract explicit. The
built-in HTS and MANUS providers use
`openxr_anatomical_wrist`: local articulation vectors and the wrist quaternion
therefore describe the same anatomical wrist axes. Fusion rejects a mismatch
unless an explicit rigid `ArticulationFrameTransform` is configured; it never
assumes that two vendor-local wrist frames are interchangeable.

The `quest` source name selects the Meta Quest Hand Tracking Streamer (HTS)
receiver (the `hts.yaml` preset selects it for both articulation and wrist
pose); `quest` does **not** mean a native OpenXR provider. The legacy
`--source hts|ovxr` flag and the `hts` alias have been removed. Articulation
can instead come from the MANUS SDK
sidecar, while wrist pose can independently come from HTS/Quest or, in MANUS
Remote mode, from the VIVE Tracker Ultimate baked into MANUS Core's raw
skeleton. Additional articulation sources can run as
record-only comparison streams. A missing or invalid explicitly selected
source is an error, and staleness is an error by default. The optional
`--stale-frame-policy hold` pauses control only when native hand/EMG recording
is disabled; comparison recordings remain strict so they cannot silently gain
source gaps. The runtime never changes sources or retargeters as a fallback.

The module boundaries are:

- `tracking`: lifecycle-managed HTS and MANUS Remote/Integrated producers;
  canonical articulation/wrist types; and timestamp-aware fusion.
- `retargeting`: packaged configurations, URDFs, Pinocchio kinematics, and the
  NLopt optimizer for Shadow, Sharpa, and Wuji, plus the optional Sharpa
  DexPilot backend.
- `hands`: named joint-count and execution-order contracts.
- `omnigibson`: the initial right-hand Sharpa execution adapter and launcher.
- `arat`: the 19-activity catalog, 6/4/6/3 subscale grouping, and version-1
  per-task ARAT scene resolver.

There is no runtime import, path lookup, or package dependency on an external
AnyDexRetarget checkout. Solver errors and unavailable/stale selected tracking
sources are reported; they do not trigger another source or command fallback.

HTS wrist and landmark lines carrying the same source frame ID (`f`) and
monotonic nanosecond timestamp (`t`) are assembled as one hand pose. The raw
values are retained on `HandFrame.source_frame_id` and
`HandFrame.source_timestamp_ns`; `HandFrame.timestamp` maps the HTS clock into
the desktop monotonic clock domain, while `HandFrame.receipt_timestamp` records
when the complete pair became available on the desktop. Input freshness uses
receipt time rather than the aligned capture time. Every hand record must carry
both metadata fields, and the wrist and landmarks metadata must match exactly;
missing or inconsistent metadata fails the HTS source instead of falling back
to arrival-order pairing. A UDP datagram must contain the complete pair. TCP
may split the two newline-delimited records across reads, but a mismatched pair
or a connection that stalls or closes mid-pair also fails the source. Enable
header/debug metadata in the HTS app.

## Installation

Install the package and its direct retargeting dependencies through the
repository setup script:

```bash
./setup.sh --dex-teleop
```

For the OmniGibson ARAT launcher, install it together with OmniGibson and BDDL:

```bash
./setup.sh --new-env behavior_dex --omnigibson --bddl --dex-teleop
```

The flag performs an editable install of `dex_teleop`; its package metadata
installs NLopt, Pinocchio (`pin`), SciPy, PyYAML, and NumPy below version 2.
The ignored runtime datasets `datasets/arat-assets-v1` and
`datasets/arat-task-instances` are separate and are not downloaded or
generated by this flag.

### Retargeter choices

`--retargeter adaptive` is the default, in-tree NLopt + Pinocchio solver. It is
the existing, tested path and supports the Shadow, Sharpa, and Wuji hand
models. Use it when preserving current behavior or selecting a hand other than
Sharpa matters.

`--retargeter dexpilot` selects the optional vector-objective implementation
from `dex-retargeting==0.4.6`. The packaged configuration currently supports
only Sharpa. Version 0.4.6 is pinned because it is compatible with the NumPy 1.x
and Pinocchio stack in Isaac Sim 5.1; it is not installed by default:

```bash
conda run -n behavior_dex python -m pip install -e './dex_teleop[dexpilot]'
```

DexPilot is useful for side-by-side backend experiments, but choosing it adds
an external package and currently narrows hand-model support. Both current
objectives ultimately use the 21 MediaPipe-equivalent joint positions;
DexPilot receives them through the rich-observation interface, while adaptive
retains its unchanged `HandFrame` input. Backend construction failures are
reported and do not fall back to `adaptive`.

### Tracking process, retarget rate, and smoothing

Both launchers parse, fuse, and retarget hand tracking in a child process by
default (`--tracking-process`). In the simulator's process that Python work
competes with OmniGibson's per-step Python for the interpreter lock; on the
hand bench it tripled the step time (17 ms to 54 ms). The child forwards each
native sample it records before the command that uses it, so recordings and
provenance rows are identical to the single-process worker, which
`--no-tracking-process` restores.

`--retarget-once-per-step` retargets only the newest frame, at most once per
simulator step, instead of every frame; an unread command never blocks
retargeting for more than 0.1 s. It saves CPU at the cost of up to one step of
extra command age, so it is off by default; with `--no-tracking-process` it
roughly halves the step time.

The adaptive retargeter's low-pass filter is time-based: `lp_alpha` applies per
`1/lp_reference_hz` seconds of capture time (`sharpa.yaml`: 0.2 per 1/60 s, a
75 ms time constant), so smoothing does not change with the retarget rate.

Each launcher freezes the objects left by loading the scene (`gc.freeze()`)
before its control loop. Python's full garbage collections then skip them;
otherwise one collection walks about 1.4 million objects and stalls the loop
and the tracking readers for about half a second.

### MANUS Remote/Integrated tracking

The production MANUS path uses the official **Remote SDK** on Linux and MANUS
Core 3 on Windows. Core receives MANUS gloves and VIVE Tracker Ultimate through
the Windows VIVE Hub/SteamVR stack; one raw-skeleton callback provides both the
25 named wrist-local joints (`openxr25_no_palm`) and the baked tracker-driven
global wrist. Python preserves their exact callback timestamp and sequence and
fuses that declared pair without a timestamp-skew search. The original
**Integrated SDK** path remains the default, gloves-only fallback.

A small mode-specific C++ sidecar calls `CoreSdk_InitializeCore` (Remote) or
`CoreSdk_InitializeIntegrated` (Integrated), validates topology, versions and
the applicable license, and sends a versioned JSON-lines stream to Python.
Remote discovery is performed by the SDK and may be selected deterministically
by discovered IP, exact name, or sorted index; this project does not guess a
MANUS port.
The proprietary MANUS headers, shared library, calibration, and license data
remain outside this repository and are never copied into an HDF5 recording.
Automatic bridge building requires a C++17-capable `g++` toolchain in addition
to the Python package dependencies.

SDK discovery checks an explicit `--manus-sdk-root`, `MANUS_SDK_ROOT`,
`~/Desktop/emg/manus`, and `~/manus_setup`. A prompt-only directory such as
`~/Desktop/emg/manus` is accepted as a discovery starting point; the installed
SDK may live below `~/manus_setup/vendor`. Build the sidecar once with:

```bash
bash dex_teleop/src/dex_teleop/native/manus_bridge/build_manus_bridge.sh \
  --mode integrated --sdk-root ~/Desktop/emg/manus
bash dex_teleop/src/dex_teleop/native/manus_bridge/build_manus_bridge.sh \
  --mode remote --sdk-root ~/Desktop/emg/manus
```

The default executables are
`~/.cache/dex_teleop/manus_bridge/manus_bridge` and
`~/.cache/dex_teleop/manus_bridge/manus_bridge_remote`. Private,
mode-specific RPATH directories prevent one SDK variant from silently
substituting for the other. Remote also requires the MANUS-documented gRPC,
Protobuf, ZeroMQ, and zlib runtime libraries.

Use `--manus-mode remote` and `--manus-core-host` for Core; the raw-skeleton
hand motion is derived (`tracker` whenever MANUS supplies a wrist). Selecting
MANUS as a wrist source also requires `--manus-expected-tracker-id` and
`--manus-expected-tracker-user-id`; geometric calibration cannot redefine the
mandatory selected-hand/OpenVR tracker policy. Without
`--manus-core-calibration` a built-in default rotates Core's Y-up world into
the launcher's Z-up tracking frame (yaw and position are anchored at
engagement, as for Quest); a measured file is only needed for a surveyed robot
frame. `--manus-calibration` remains the selected glove's `.mcal` file. See the
[MANUS Core + Ultimate runbook](docs/manus-remote-vive-ultimate-runbook.md)
for Windows setup, calibration schema, diagnostics, launcher examples, and
hardware acceptance checks.

### VIVE Tracker Ultimate wrist pose

The Ultimate is not a launcher source of its own. It is paired in VIVE Hub on
the Windows host, its pose reaches MANUS Core through SteamVR, and the Remote
sidecar receives the tracker-driven global wrist together with the glove
articulation in one callback (see the MANUS section above and the runbook).
The earlier lighthouse provider that read base-station trackers directly
through `pysurvive`/libsurvive (`--wrist-source vive`, `--vive-calibration`,
`calibrate_vive.py`) has been removed. Use `--wrist-source quest` to use the
wrist pose carried by HTS instead.

### Launch presets

`launch_og.py` reads a YAML preset from `dex_teleop/configs/` before parsing
the command line: `manus_core.yaml` (the default; MANUS gloves + Ultimate
through Windows Core) or `hts.yaml` (Quest hand and wrist), selected with
`--config <name|path>`. Keys are the option names with the leading dashes
removed; `null` keeps the built-in default; command-line flags override the
file; `--no-config` starts from the built-in defaults. `--view-only` and
`--list-tasks` never apply a preset. See `guide.md` section 0.

## ARAT launcher

Run from the BEHAVIOR-1K checkout root in the `behavior_dex` environment. The
launcher requires `datasets/arat-assets-v1` and `datasets/arat-task-instances`
in this checkout. It does not
search other checkouts, legacy `custom-assets`, or an external
AnyDexRetarget repository.

For the complete input-source matrix, synchronization rules, retargeting paths,
record-only behavior, and HDF5 layout, see [the `launch_og.py` input-source guide](guide.md).

List the activities and their 12 physical layouts:

```bash
python dex_teleop/scripts/launch_og.py --list-tasks
```

Run one item-level BehaviorTask:

```bash
python dex_teleop/scripts/launch_og.py \
  --config hts \
  --task arat_grasp_block_10cm \
  --hand-model sharpa \
  --recording-path outputs/arat_grasp_block_10cm.hdf5
```

Press SPACE to engage and start recording (there is no automatic engagement),
R to end the episode and reset, Ctrl+C to finalize the file.

`--config hts` selects HTS for both roles (the preset already enables
`--record-hand-poses`). Select the roles independently for a mixed setup. For example,
this controls hand articulation with MANUS, controls the wrist with the Quest
pose carried by HTS, retargets through the recommended rich-observation
DexPilot path, and also records Quest articulation for comparison:

```bash
python dex_teleop/scripts/launch_og.py \
  --task arat_grasp_block_10cm \
  --hand-source manus \
  --wrist-source quest \
  --record-hand-source quest \
  --retargeter dexpilot \
  --manus-calibration /path/to/right-hand.mcal \
  --record-hand-poses
```

This example requires the optional `dex-teleop[dexpilot]` extra shown above.
Omit `--retargeter dexpilot` to retain the compatible default adaptive
NLopt + Pinocchio path.

For the MANUS + Ultimate path, use the default `manus_core` preset (or
`--wrist-source manus --manus-mode remote` with the Core-world calibration and
tracker policy flags) and retain
`--record-hand-source quest` if HTS articulation should run as a comparison
stream. Also pass `--record-wrist-source quest` to retain the corresponding
Quest wrist trajectory. Both record-only options are repeatable and acquire
their named component at native rate; neither changes the source driving the
robot. Fusion matches the selected wrist pose to articulation timestamps and
enforces `--maximum-source-skew`.
For a provider whose declared local basis differs from the selected anatomical
wrist, pass `--articulation-wrist-calibration` with a schema-version-1 JSON
rigid transform:

```json
{
  "schema_version": 1,
  "source_frame": "vendor_wrist",
  "target_frame": "openxr_anatomical_wrist",
  "translation": [0.0, 0.0, 0.0],
  "quaternion_xyzw": [0.0, 0.0, 0.0, 1.0]
}
```

The transform is applied before either retargeter and its file hash is stored
with the recording. Identity is accepted only when both frame identifiers
already match.
MANUS callback time is host `CLOCK_MONOTONIC`; HTS maps its source monotonic
clock into that domain from receive timing. This is software synchronization,
not a hardware trigger, so transport-delay bias remains visible in the saved
capture/receipt timestamps and should be measured when comparing devices.

The launcher records automatically to
`dex_teleop/outputs/recordings/<task>.hdf5`. Override that destination with
`--recording-path` when running a single `--task`. OmniGibson's
`HDF5CollectionWrapper` records every teleoperated step's action, serialized
simulator state, reward, and terminated/truncated flags. Pressing `R` flushes
the current episode before resetting, and exiting normally or with Ctrl+C
flushes and closes the current recording. A subscale run creates a separate
default HDF5 file for each activity so every file retains the correct task and
scene metadata.

Wrist translation uses `1.5x` sensitivity by default, measured from the pose at
engagement. Use `--position-sensitivity 1.0` for one-to-one motion, or a larger
finite positive value if more gain is needed. The gain applies to all three
translation axes and does not expand the Franka workspace.

The Franka starts in the `extended` reset pose (Deoxys tabletop golden joints).
Pass `--reset-pose compact` for the OmniGibson `franka.yaml` ready pose.

Press `T` to show or hide the post-filter commanded-target marker and `E` to
show or hide the measured EEF marker while teleoperating; no visualization flag
is required. Each marker combines three pose-oriented wrist circles with red X,
green Y, and blue Z axes. The commanded circles and origin are magenta; the
measured circles and origin are cyan. Their connecting line is green below 2 cm
of position error, amber from 2-5 cm, and red above 5 cm. Pass
`--visualize-arm-markers` to start both frames visible instead of hidden. The old
`--visualize-arm-workspace` option remains as an alias, but no workspace geometry
is generated.

Pass `--record-hand-poses` to retain both the selected action-rate pose and the
independent source-rate streams. One compatibility sample per recorded action
is stored under `human_hand_pose/demo_N`. The canonical
`wrist_position`, `wrist_quaternion_xyzw`, and `landmarks` datasets use the
source-independent right-handed world frame; landmarks have shape
`(steps, 21, 3)` in the `landmark_names` order stored on the group. HTS also
stores its source-native Unity values in `raw_wrist_position_unity`,
`raw_wrist_quaternion_xyzw`, and `raw_landmarks_unity`. Timestamps, source frame
IDs, confidence, and a `raw_available` mask are recorded alongside them. The
raw arrays are available only when the same HTS receiver supplies both selected
articulation and wrist roles. In a MANUS-articulation + Quest-wrist run they are
NaN with `raw_available=false`; the independent canonical Quest comparison is
still complete under `/hand_tracking`. The flag is opt-in, so recordings made
without it retain the existing layout.

The same file's `/hand_tracking` schema version 1 preserves every configured
native source stream without resampling and records derived control streams at
their processing cadence:

- `articulation_streams` contains selected and record-only sources such as
  MANUS and Quest/HTS, including named joints, validity, and source timing.
- `wrist_streams` contains the acquired wrist streams and the exact fused wrist
  pose used for control.
- `retargeting_streams` stores named robot-joint results and the articulation
  and wrist row references that produced each result.
- `action_alignment/demo_N` references the exact articulation, wrist, and
  retargeting rows selected for every OmniGibson action. Repeated references
  are expected when simulation steps faster than a tracker.

Acquisition threads feed bounded, loss-detecting queues, so time spent in an
optimizer does not silently overwrite intermediate device samples. Queue
overflow fails the run instead of producing an incomplete comparison. This
layout supports a synchronized MANUS-versus-Quest comparison while preserving
each sensor's native cadence. `/human_hand_pose` remains for
existing analysis code and represents only the selected control observation;
it is not a substitute for the multi-source streams.

### Synchronized OYMotion EMG

The Synchroni SDK stays an external dependency; it is not copied into this
repository or imported into the Isaac Sim process. `launch_og.py` starts a
clean `behavior_dex` Python sidecar that owns Bluetooth and the SDK event
loops, writes native-rate EMG to a temporary HDF5 file, and sends only a
bounded waveform preview to Kit over localhost UDP. Install the SDK and its
dependencies into `behavior_dex`, for example from the adjacent checkout:

```bash
conda run -n behavior_dex python -m pip install -e ../synchroni-sensor-sdk
```

Alternatively, install `bleak>=3.0.2` and `flatbuffers>=25.0.0` in that
environment and pass `--emg-sdk-path ../synchroni-sensor-sdk`. Start one
single-task recording with:

```bash
conda run -n behavior_dex python dex_teleop/scripts/launch_og.py \
  --config hts \
  --task arat_grasp_block_10cm \
  --emg \
  --emg-device D8:71:4D:8D:99:92 \
  --emg-adapter hci0 \
  --emg-sdk-path ../synchroni-sensor-sdk \
  --recording-path outputs/arat_grasp_block_10cm_emg.hdf5
```

If exactly one supported `OY*`, `Sync*`, or `gForce*` device is visible, it is
selected automatically. Use `--emg-device` with a name substring or Bluetooth
address when multiple bands are present. On Linux, `--emg-adapter` selects the
BlueZ adapter; it defaults to `hci0`. This workstation's OYWW1000 is
`D8:71:4D:8D:99:92` and should use `hci0`. `--emg` also enables hand-pose
recording. The native `omni.ui.Plot` monitor is docked to the right of the
left-shoulder viewport in the first row and refreshed at 10 Hz without
downsampling the saved data. Each channel row shows the latest electrode
impedance using the SDK
example's contact colors: green through 500 kΩ, orange through 999 kΩ, and red
above 999 kΩ. Use `--no-emg-display` to record without the dock. No PyQt or
Matplotlib GUI is launched.

Dock placement is camera-rig-specific. With the default `arat_default` rig,
the EMG monitor is added to the
lower `Content` / `Console` tab stack, so it can be selected by clicking its
`OYMotion EMG` tab. The legacy `arat_sharpa_v1` rig retains the placement
described above the left-shoulder viewport.

The launcher explicitly configures and verifies every firmware filter before
starting notifications. Its default is every filter on: the 0.5 Hz HPF, the 80 Hz LPF, the 50 Hz
and the 60 Hz notch (as HandSync records; until 2026-11-15 the 50 Hz notch was off by default). Use `--no-emg-hpf`, `--no-emg-lpf`, or
`--emg-notch {off,50,60,both}` to select a different reproducible policy. The
verified aggregate state is printed at startup and stored as
`/emg.attrs['filter_configuration']`; acquisition fails instead of silently
continuing if the wristband reports a different state.

Pass `--display decoder` (or the existing `--visualize-decoder` spelling) to
load the sibling `emg2pose` checkout and its
`checkpoints/regression_vemg2pose.ckpt`, decode the same EMG samples being
recorded, and render the UmeTrack hand mesh. In the mobile-manipulator rig,
`EMG2Pose Hand` is another clickable tab in the lower `Content` / `Console`
stack; the existing rig retains its prior placement below the waveform monitor.
The model needs about 5.9 seconds of source history before its first pose.
Inference runs in the EMG sidecar, so it does not create a second BLE
connection. Override the defaults with `--emg2pose-root`,
`--emg2pose-checkpoint`, or `--emg2pose-device cpu` as needed. Decoding targets
5 Hz by default. `--emg2pose-inference-hz 10` is a conservative faster setting
on CUDA; the 32-sample, 500 Hz wristband callbacks cap meaningful fresh-window
updates at about 15.6 Hz. The decoded mesh is a live diagnostic; the lossless
native EMG remains the recorded source of truth.

The combined recording contains:

- `/data/demo_N/action`: the exact command passed to `env.step` by the existing
  OmniGibson wrapper.
- `/human_hand_pose/demo_N`: the compatibility pose selected for each action,
  including integer `timestamp_monotonic_ns` and `receipt_monotonic_ns` values.
- `/hand_tracking`: all configured articulation, wrist, fused-control, and
  retargeting streams, plus exact per-action row references. Native
  articulation and wrist streams retain acquisition cadence; fused-control and
  retargeting streams retain their derived processing cadence. This group is
  present when multi-source hand recording is enabled.
- `/action_timing/demo_N`: desktop monotonic timestamps immediately before and
  after each `env.step`, plus simulator time before and after the step.
- `/emg/samples`: converted microvolt values, raw ADC values, SDK sample index
  and timestamp, loss flags, and an estimated desktop monotonic timestamp at
  the wristband's native sample rate. `/emg/batches` preserves callback receive
  time and per-channel diagnostics.
- `/synchronization/demo_N`: half-open EMG row ranges for the episode and for
  every action row.

Linux `time.monotonic_ns` is shared across the launcher and sidecar processes.
The Synchroni SDK timestamp is device-stream-relative rather than a desktop
epoch, so the recorder maps SDK sample indices at the advertised sample rate
to the callback having the smallest observed receive delay. It retains the raw
SDK and callback timestamps so a different clock model can be fit offline.
This is host-clock synchronization and includes unknown Bluetooth transport
latency; it is not hardware-trigger or PTP synchronization.

Each action also records an evaluation trace under `evaluation/demo_N/steps`.
The trace expands every BDDL goal condition into its natural-language text and
satisfaction state, and stores the full ARAT snapshot, provisional score,
decision reasons, scoring-rule conditions, hand contacts, apertures, object and
target evidence, hold quality, release state, water state, and milestone event
history. The ARAT portion is marked disabled when teleoperation uses
`--no-score`.

Ctrl+C is handled as a graceful stop request: the active simulator operation
finishes, the HDF5 trajectory is closed, and only then does OmniGibson shut
down. Collection writes to a hidden same-directory staging file and atomically
replaces the requested `.hdf5` only after a successful close. A crash therefore
cannot truncate a previously completed recording at the final output path.

During teleoperation, the large left-shoulder view also displays each BDDL goal
condition. Unsatisfied conditions are red and satisfied conditions are green;
the terminal prints the satisfied-condition count whenever it changes.

Replay a recording and render the recorded simulator states into one MP4. The
configured main camera spans the center, with left/right shoulder cameras above
the corresponding thumb-side/pinky-side wrist cameras:

```text
left shoulder |       main       | right shoulder
thumb wrist   |                  | pinky wrist
```

```bash
python dex_teleop/scripts/replay_data.py \
  dex_teleop/outputs/recordings/arat_grasp_block_10cm.hdf5 \
  --headless \
  --evaluation-overlay
```

When `--episode-id` is omitted, the script lists all saved episodes and prompts
for the episode ID before launching OmniGibson. The video is written next to
the recording as `<recording>_demo_<episode>.mp4`. Use `--episode-id` for a
non-interactive selection, `--list-episodes` to only inspect the recording, or
`--output` to override the MP4 path. The replay script infers and validates the
ARAT task from the HDF5 metadata; an optional `--task` can assert the expected
activity.

`--evaluation-overlay` adds a per-frame dashboard below the camera mosaic. It
shows every BDDL predicate as PASS/FAIL and explains the provisional ARAT score
with each applicable scoring gate, its threshold and measured evidence, current
contacts and hold/release state, and milestone events. `--log-eval` is retained
as a shorter alias. Recordings created before evaluation traces were introduced
must be recorded again to use this overlay.

Conditions that do not apply to the selected task are omitted, while the set of
rows for that task remains fixed throughout the video. Rows are separated by
`SCORE 1`, `SCORE 2`, and `SCORE 3` headers. A white `WAIT` therefore means that
an applicable condition cannot be decided yet, such as release quality before
a release has occurred.
The evaluation dashboard retains its original 600-pixel height and uses text
scaled to 1.5 times the initial size; the four camera images retain their
original resolution. Individual BDDL goal rows use the same regular-weight
body font as the ARAT calculation rows.

The default launcher uses the chest camera as its large main view, with the
left- and right-shoulder cameras docked on their corresponding sides. The
thumb- and pinky-side cameras are rigidly mounted to the Sharpa palm base and
stacked below the right-shoulder view. They converge toward the fingertips and
nearby manipulation workspace. Press `B` to toggle the main viewport between
the chest and overview cameras. The legacy `arat_sharpa_v1` rig remains
selectable with `--camera-rig arat_sharpa_v1`.

Camera poses, calibration, viewport docking, panel docking, and toggle cycles
are defined in packaged YAML files under `src/dex_teleop/arat`. The legacy rig
remains in `camera_rigs.yaml`; the default mobile-manipulator layout is defined
in `arat_default.yaml` under the `arat_default` rig ID.
`arat/tasks.yaml` selects a default `camera_rig`, an individual task may
override that field, and `--camera-rig` may override it for one launch. A
camera's `parent.frame` is either `scene` for a fixed world camera or
`robot_link` with a `link` name for a rigidly mounted camera. Each `teleop` or
`view_only` layout maps named viewports to cameras and describes auxiliary
docking. A toggle entry specifies one keyboard `key`, the target `viewport`,
and the ordered `cameras` to cycle; its first camera must be that viewport's
initial camera.

Launch the default R1-Pro-style mobile-manipulator layout with:

```bash
python dex_teleop/scripts/launch_og.py \
  --task arat_grasp_block_5cm
```

Its main viewport starts from above the reset hand, centered horizontally on
the ARAT toolbox and looking downward like a standing operator looking at
their hands, with the Franka acting as the robot's right arm. Press `B` to
toggle that viewport to the farther JoyLo-style
overview and back. The left column contains the left-shoulder view. The right
column contains the right-shoulder view above the robot-linked thumb- and
pinky-side wrist cameras. Add `--emg --display decoder` to expose the waveforms
and decoded hand as clickable tabs in the lower dock.

The `arat_default` workspace uses JoyLo's viewport-only Kit layout: Stage,
Layer, Property, Render Settings, and the other editor panels are hidden. It
also uses JoyLo's 1080-square main render, 256-square auxiliary renders,
left/right dock ratios of 0.25/0.20, with the two wrist views evenly split.
Viewport
textures retain those fixed square resolutions, matching JoyLo rather than
adopting the docked panels' aspect ratios. Rectangular panels therefore show
black letterboxing around the square views. When `--emg` is active and its
display is enabled, Content and Console are restored so `OYMotion EMG` and
`EMG2Pose Hand` can share that lower tab stack.

To inspect a saved task layout without starting HTS, loading a robot, or
initializing a BehaviorTask, use the camera-only viewer:

```bash
python dex_teleop/scripts/launch_og.py \
  --task arat_grasp_block_10cm \
  --view-only
```

Because view-only mode intentionally omits the robot, its right-lower viewport
is empty. The fixed chest view remains in the center with the left- and
right-shoulder cameras docked beside it. Press `B` to toggle the center
viewport between chest and overview.

Run every activity in a subscale in the same process, using a fixed number of
simulation steps per item:

```bash
python dex_teleop/scripts/launch_og.py \
  --config hts \
  --subscale grasp \
  --steps-per-task 3600
```

The launcher forces `OMNIGIBSON_DATA_PATH` to this checkout's `datasets`
directory and fails if it was explicitly pointed elsewhere. OmniGibson loads
the task objects from `arat-assets-v1` and composes the robot as `model: franka`
with `end_effector: sharpa_right` from `omnigibson-robot-assets`, matching the
established ARAT HTS launcher. Each activity loads
its own plain `Scene` template, including the grey floor and prior ARAT lighting, and embeds the explicit
BDDL-instance-to-object-name map before the BehaviorTask is initialized.

All 19 BDDLs carry real completion goals ("object placed at its ARAT target and
released", expressed with `onshelf` / `ontop` / `pegged` / `filled` /
`not touching`), and `arat/tasks.yaml` declares `placeholder_goals: false`. On
top of BDDL completion, the launcher runs the ARAT 0-3 scorer
(`dex_teleop.arat.eval`) by default during teleoperation:

- Each item runs on a 60 s engaged-time clock (only engaged steps count);
  completion in under 5 s with the item's appropriate hand-movement components
  scores 3. Scoring rules follow `ARAT_scoring_guide.md`; only hand-movement
  components (pad contacts, grasp taxonomy, voluntary opening) gate scores —
  arm-movement quality is deliberately not evaluated.
- Milestones (first hold-and-lift, drops, release, fumbles, spills) are printed
  live and recorded per item to `outputs/arat_results/<timestamp>/<activity>.json`
  (`--results-dir` overrides the base directory, `--no-score` disables scoring).
- `--subscale` runs apply the ARAT administration protocol: a 3 on the first
  item credits the subscale maximum and skips the rest; a 0 on the second item
  (or on the first gross-movement item) ends the subscale with 0. The session
  summary is written to `session.json`.
- Pressing `R` resets the item's scorer along with the scene.

`quest` means HTS, not OVXR; the former `--source ovxr` stub has been removed.
A future native OVXR provider should implement the articulation and/or wrist
source contracts; fusion, retargeting, recording, and the Sharpa execution
adapter do not need to change.

## Sharpa hand bench (finger tracking only)

`dex_teleop/scripts/launch_hand_bench.py` loads a scene that is unrelated to
ARAT: one right Sharpa hand fixed upright above a plain wooden table
(`desk/arat_standard_table` from `datasets/arat-assets-v1`, used only as a
generic table), a dark grey floor as backdrop, three sphere lights, and no
skybox. The hand is the `franka` + `sharpa_right` model from
`omnigibson-robot-assets`; the Franka, its pedestal, and the ARAT wrist-camera
pods are hidden at load time, and the arm is held at a fixed configuration by
a `NullJointController`, so the environment's action space is exactly the 22
Sharpa finger joints. The scene, the held configuration, the expected palm
pose, and the camera rig live in `src/dex_teleop/hand_bench/hand_bench.yaml`;
the launcher asserts the tabletop height, the palm pose, and that nothing
touches the table before it starts.

Wrist tracking is disabled by construction. Only `--hand-source quest|manus`
selects tracking; `--wrist-source`, the MANUS tracker options,
`--tracking-yaw-deg`, and the other wrist-only flags are rejected with an
explanation. The selected articulation source is wrapped in
`FixedWristSource`, which pairs every articulation sample with a constant
identity wrist, so `MultiSourceTrackingWorker`, fusion, and both retargeters
run unchanged and the wrist pose carried by Quest or the MANUS IMU is
discarded rather than used.

```bash
# Quest HTS fingers (default), UDP 9000
conda run -n behavior_dex python dex_teleop/scripts/launch_hand_bench.py

# MANUS glove fingers (Integrated SDK sidecar)
conda run -n behavior_dex python dex_teleop/scripts/launch_hand_bench.py \
  --hand-source manus --manus-calibration /path/to/right-hand.mcal

# Inspect the scene without any tracking hardware
conda run -n behavior_dex python dex_teleop/scripts/launch_hand_bench.py --view-only

# Render the default and egocentric views to PNG (works headless) and exit
OMNIGIBSON_HEADLESS=1 conda run -n behavior_dex \
  python dex_teleop/scripts/launch_hand_bench.py --screenshot-dir dex_teleop/outputs/hand_bench
```

The main viewport starts on the `dorsal` camera (behind the back of the hand,
29 degrees above it). Press `B`, the same key JoyLo and the ARAT launcher use,
to toggle to the `palmar` egocentric camera on the operator's side and back.
Fingers start following the first fresh frame; `SPACE` pauses and resumes,
`R` reopens the hand and resets the retargeter, and Ctrl+C exits. A stale
articulation stream is an error by default (`--stale-frame-policy hold` holds
the last pose instead), `--retargeter dexpilot` selects the optional backend,
`--finger-target-scale` shrinks the commanded flexion, and `--show-arm` keeps
the Franka visible when debugging the hidden mount.
